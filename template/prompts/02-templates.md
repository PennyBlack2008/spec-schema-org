# 문서 양식

## A. 브리핑 — `log/briefings/<단계>-iter<k>.md`
```markdown
# <단계> 브리핑 (반복 k) — <역할명>
## 1. 받은 인풋
- 파일: ...
- 핵심 요약: ...
- 내가 이해한 범위 / 애매한 곳: ...
## 2. 예외 시나리오 제안
| 제안ID | 시나리오 | 깨지는 지점(테이블·제약) | 근거 REQ | 기존 SCN 참조 |
## 3. 부장님께 질문
- Q1. ... (관련 REQ: ...)
## 4. (회귀 시) 받은 리젝과 재작업 계획
| REG | 리젝 내용 | 고칠 곳 |
```

## B. 토론 기록 — `log/discussions.md` (append)
```markdown
## <단계> · 반복 k · 토론
- 인풋 이해 교정: ... (근거 REQ/행)
- 질의응답: Q1 → 답 (근거: REQ-..., sheets/xx.md#행) / DEC-nnn
- 시나리오 판정:
  | SCN | 판정(반영 필요/수용 리스크/범위 밖) | 이유 | 반영 대상 단계 |
- 부장 추가 시나리오: SCN-...
- 이번 단계 수행 지시: ...
```

## C. 시나리오 — `log/scenarios.md` (append)
```markdown
### SCN-nnn <제목>
- 제안: <단계>/<부장> · 근거 REQ: ...
- 상황: ...
- 깨질 수 있는 것: ...
- 판정: 반영 필요 | 수용 리스크 | 범위 밖 (DEC-...)
- 해결 상태: 미해결 → (S3 iter2 에서 <테이블.컬럼/제약> 으로 해결, S6 테스트 T-nn 으로 확인)
```
상태는 append 로 갱신한다: `- 상태 갱신(S6 iter1): 해결 확인 T-07`.

## D. 결정 — `log/decisions.md`
```markdown
### DEC-nnn <제목>
- 유형: 모호 해석 | 모순 사용자결정 | 잠정(사용자 미결정) | 리젝 중재 | 수용 리스크 | 에스컬레이션
- 근거: REQ-..., CON/AMB-..., 원문 인용
- 결정: ...
- 영향 테이블: ...
- 대체: (있으면 이전 DEC)
```

## E. 가정 — `log/assumptions.md`
```markdown
### ASM-nnn <제목>
- 왜 필요: (화면 기획 없음 / 정본 누락 GAP-...)
- 가정: ...
- 깨지면 바뀌는 것: (테이블·컬럼)
- 확인할 사람/시점: (화면 기획 / 법무 회신 / 사용자)
```

## F. 모순·모호·누락 — `log/contradictions.md`
```markdown
### CON|AMB|GAP-nnn <제목>
- 원문 A: "..." (REQ-..., sheets/xx.md 행)
- 원문 B: "..." (REQ-..., sheets/yy.md 행)
- 왜 문제인가 / 스키마 영향: ...
- 부장 권고안: ... / 대안: ...
- 상태: OPEN | DEC-nnn 로 처리
- 사용자 결정: 
```

## G. 회귀 — `log/regressions.md`
```markdown
### REG-nnn <from 단계> → <target 단계> (반복 k)
- 판정자: 부장 게이트 | S4 | S5 | S6 | 부장 중재 | 최종 평가
- 문제: ...   근거: REQ-... / 파일·행 / 실행 로그
- 영향 테이블: ...
- 해결: (target 단계 재작업 후 append) "S3 iter3 에서 ... 로 수정"
```

## H. 진행 상태 — `log/run-state.md` (append, 스크립트 단계마다 부장이 한 줄)
`- <단계> iter k: PASS | REJECT→<target> (REG-...) | ESCALATE(proceed/stop)`

## I. 전체 관계도 문서 — `S7-docs/01-관계도.md`
```markdown
# <cfg.project> — DB 전체 관계도
- 기준: `cfg.db.schemaFile` (반복 k), 정본 버전, 기존 스키마 스냅샷 SHA
## 1. 한눈에 (도메인 묶음 다이어그램)
## 2. 도메인별 ERD (mermaid erDiagram, 도메인당 1개 + 도메인 간 연결 1개)
   기존 테이블은 이름 앞에 `[기존]`, 변경된 기존 테이블은 `[기존*]`. **등급을 색이나 접두로 구분**: 확정(<me>) / 예상(담당자명) / 기존
## 3. 핵심 흐름 (대표 주체 1건이 생성부터 종료·파기까지 거치는 테이블 경로)
## 4. 관계 목록 표 | 부모 | 자식 | 카디널리티 | FK 컬럼 | onDelete | 근거 REQ | 경계(확정↔예상 여부) |
## 4-1. 담당 경계 — 확정↔예상 관계와 경계 계약 요약, 상대 설계가 달라질 때 끊는 지점
## 4-2. 테이블 수 — 기준선(데이터모델 시트) 대비 증감 표
## 5. 관계 수준의 아리까리한 부분 (ASM/AMB 링크)
## 6. 관계 수준의 주의점 (순환 참조, 다형 참조, soft delete 전파, 파기 시 FK 처리 등)
## 7. 회귀 이력 요약 (관계 관련 REG)
## 8. 정본 커버리지 요약 (S4 매트릭스 링크)
```

## J. 테이블 명세 — `S7-docs/tables/<ModelName>.md`
```markdown
# <ModelName> (`<db_table_name>`)  [신규 | 기존 | 기존 변경] · [확정: <me> | 예상: <담당자>]
> (예상 등급이면) 이 문서는 <담당자> 영역의 예상안이며 실제 설계는 담당자가 결정한다.
- 담당 근거: 데이터모델 시트 #행 / REQ-...   분리 근거(공통 규칙 §12): 번호
- 도메인: ...   엔티티: ENT-...
- 한 줄 목적: ...
- 근거 REQ: REQ-..., ...
- 생명주기: 생성(누가/언제) → 변경 → 종료 → 보존기한 → 파기 방식

## 컬럼
| 컬럼(필드 / db명) | 타입 | NULL | 기본값 | 키/인덱스 | 설명 | 근거 REQ | 아리까리한 부분 |
(아리까리한 부분: 해석이 갈리는 점, 값 목록 미확정, 화면 기획 의존 → ASM/AMB/DEC 링크. 없으면 "—")

## 관계 | 대상 | 카디널리티 | FK | onDelete/onUpdate | 비고 |
## 인덱스·유니크 제약 | 이름 | 컬럼 | 목적(어떤 조회/어떤 무결성) |
## 상태값·코드값 (있으면) | 값 | 의미 | 전이 가능 상태 | 근거 |

## 화면·컨셉 변경 시 영향
| 예상 변경 | 이 테이블 영향 | 마이그레이션 크기(컬럼 추가만/의미 변경/구조 변경) | 흡수 장치(코드 테이블·JSON·nullable·계산값) |
## 다른 담당 테이블과의 경계 (있으면)
| 상대 테이블 [예상: 담당자] | 참조 키 | 최소 가정 | 상대가 다르게 만들면 |

## 이 테이블에서 주의할 점
- 동시성·멱등·권한 스코프·개인정보(암호화/마스킹/파기)·대량 적재·코드값 변경 영향 등
- 관련 SCN: SCN-... (어떻게 막는지 / 앱 레이어 책임인지)

## 아웃풋 과정에서 생긴 회귀
| REG | 단계 흐름 | 무엇이 문제였나 | 어떻게 바뀌었나 |
(없으면 "회귀 없음 — 첫 설계 그대로 통과")
```
