# S5 레드팀 (검토 단계)

## 임무
**스키마를 깨뜨리는 것**이 목표다. 운영에서 일어날 수 있는 예외를 들이대서 데이터가 깨지는 경로를 찾는다.
- 손상, 유실, 중복
- 권한 누출
- 법적 위반

## 인풋
- `cfg.db.schemaFile` 과 S3 문서 전체
- `log/scenarios.md`
- `00-spec/INDEX.md`: 특히 법률·정책·보존·동의 관련 REQ
- `log/decisions.md`, `log/assumptions.md`

## 방법
1. **기존 시나리오 재현:** 누적 SCN 중 `반영 필요` 판정을 받은 것을 모두 스키마 위에서 한 단계씩 따라가며 **실제로 막히는지** 판정한다.
2. **새 시나리오 최소 10개:** 관점은 부장 체크리스트를 쓴다.
   - 구체적인 데이터를 넣어 쓴다. 예: "주체 A 가 건 2개를 만들고, 조직 X 에 배정된 뒤 동의를 철회하고, 3년 뒤 파기 배치가 돈다."
3. **변경 내성 시나리오 최소 8개:**
   - 화면 기획 변경 5개 이상: 단계 추가·삭제, 새 필터·목록 컬럼, 필수/선택 변경, 화면 분리, 용어 변경
   - (담당 구분 시) 다른 담당자의 설계가 예상과 다른 경우 3개 이상: PK·구조가 다름, 다른 키로 조회함
   - 마이그레이션 크기로 판정한다: `컬럼 추가만` / `의미 변경` / `구조 변경`. 확정 테이블에서 `구조 변경`이 나오면 `뚫림`이다.
4. **과설계 점검:** 같은 생명주기로 합칠 수 있는 테이블, 아무도 읽지 않는 컬럼, 근거가 약한 1:1 을 찾는다. 결과는 `과설계`로 표시한다.
5. **결과 판정:** 각 시나리오는 셋 중 하나다.
   - `막힘(DB)`: 제약·FK·유니크로 막힌다.
   - `막힘(앱)`: app-enforced 규칙 번호를 댄다.
   - `뚫림`: 어디서 어떻게 깨지는지 적는다.
6. **새 SCN 등록:** `log/scenarios.md` 에 "제안" 상태로 올린다.
7. **실행 가능한 시나리오:** SQL 로 실행할 수 있는 것은 `S5-redteam/executable.md` 에 기대 결과와 함께 넘긴다.

## 아웃풋
- `S5-redteam/results.md`: | SCN | 시나리오 | 결과 | 근거(모델·제약) | 영향 | 제안 수정 |
- `S5-redteam/executable.md`

## 판정
- **리젝 (target 은 보통 S3, 개념 문제면 S2):**
  - REQ 를 위반하는 `뚫림`
  - 확정 테이블의 `구조 변경`
  - `과설계`. 단, 정본 근거가 있으면 예외다.
- **리젝하지 않음:**
  - 예상 테이블 자체의 문제. 경계 계약에 영향이 있을 때만 리젝하고, 나머지는 `escalations` 에 "타 담당 참고"로 올린다.
  - 정본 근거가 없는 순수 운영 리스크. `escalations` 에 올린다.
