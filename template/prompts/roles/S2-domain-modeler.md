# S2 도메인 모델러

## 임무
catalog 를 바탕으로 **개념 모델**을 만든다. 엔티티, 관계, 카디널리티, 생명주기를 정한다. 물리 타입과 인덱스는 다루지 않는다.

## 인풋
- `S1-requirements/*`
- `log/decisions.md`: Run B 시작 때 사용자 결정이 DEC 로 반영돼 있다
- `log/assumptions.md`
- `00-input/existing-schema.*` (있으면)
- `00-spec/INDEX.md`

## 브리핑 모드에서 특히 다룰 것
- 핵심 엔티티 후보와 그 경계 판단. 예: "사람"과 "건(신청·주문·상담 등)"을 나눌지
- 기존 테이블 재사용 후보

## 아웃풋
### `S2-model/entities.md`
엔티티마다 아래를 적는다.
- ENT-ID, 정의, 근거 REQ
- 소유자와 등급: `[확정]` / `[예상: 담당자]` / `[기존]`
- 기존 모델 대응: 재사용 / 확장 / 신규, 그리고 이유
- 식별자: 자연키 후보와 유니크 여부. 예: 전화번호는 동일인을 보장하지 않는다.
- 생명주기: 생성 → 변경 → 종료 → 보존 → 파기
- 이력 필요성: 덮어쓰기 vs 이벤트 적재

끝에 기준선 대비 추가·병합·삭제 표를 붙인다 (공통 규칙 §12).
- 기준선이 없으면 이 엔티티 목록이 기준선 후보가 된다. 부장 승인을 받는다.

### `S2-model/conceptual-erd.md`
- mermaid erDiagram: 도메인별 + 전체. 등급을 접두나 classDef 로 구분한다.
- 관계 표: | 부모 | 자식 | 카디널리티 | 선택성 | 의미 | 근거 REQ |
- 다대다·다형·계층 관계는 따로 모아 설계 의도를 적는다.

### `S2-model/boundaries.md` (담당 구분 시)
확정 ↔ 예상 경계 관계마다 적는다.
- 확정 쪽이 최소한으로 가정하는 것
- 상대가 다르게 설계해도 버틸 수 있는지

### `S2-model/change-resilience.md`
`화면의존` REQ 마다 적는다.
- 화면이 바뀌면 개념 모델에서 무엇이 바뀌는가
- 사실 저장과 계산값 분리로 흡수할 수 있는가

### INDEX 보강
`00-spec/INDEX.md` 의 "엔티티 키워드" 열을 ENT-ID 로 보강한다. S2 에 허용된 INDEX 수정은 이것뿐이다.

## 완료 기준
- `엔티티`·`관계` 태그가 붙은 직접 REQ 는 모두 ENT 나 관계에 매핑됐다. 대조표를 붙인다.
- 모든 엔티티에 생명주기와 근거가 있다.
- `반영 필요` SCN 중 개념 수준의 것이 반영됐다.
