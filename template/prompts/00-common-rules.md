# 조직 공통 규칙 (모든 직원·부장 필독)

- `BASE` = 작업 폴더. 프롬프트로 주어진다. 이 파일은 `BASE/prompts/` 에 있다.
- **프로젝트 전제는 `BASE/config.json` 에 있다. 항상 먼저 읽는다.** 이 문서에서 `cfg.x` 는 그 파일의 키를 뜻한다.

## 1. 저장 규칙 (절대)
- 이 작업의 **모든 인풋과 아웃풋은 `BASE` 안에 저장한다.** 임시 파일·스크립트·로그·SQL·덤프 전부 포함.
- `BASE` 밖의 원본(기존 저장소 등)은 **읽기만** 한다. 쓰려면 먼저 `BASE/00-input/` 에 스냅샷으로 복사하고, 출처·시각·버전(커밋 SHA 등)을 `00-input/SOURCES.md` 에 적는다.
- `BASE/spec/` 은 사용자가 넣은 정본 원본이다. 읽기만 하고 수정·이동하지 않는다.
- 이후 단계는 스냅샷만 본다. 원본을 다시 직접 보지 않는다 (재현성).

## 2. 금지
- **기존 저장소(`cfg.existingSchema.repo`)를 바꾸지 않는다.** 파일 수정·checkout·commit·push 모두 금지다.
  - 허용: `git fetch`, `git show <ref>:<path>`, `git log`.
  - 작업 트리가 다른 브랜치에 있을 수 있으니 작업 트리 파일 대신 `cfg.existingSchema.ref` 를 읽는다.
- **공유 DB(개발·운영)에 접속하지 않는다.**
  - 실제 접속 정보(`.env*`, `DATABASE_URL` 등)를 읽거나 쓰지 않는다.
  - DB 실행은 S6 의 일회용 로컬 컨테이너만, 접속 정보는 `cfg.db.dummyEnv` 만 쓴다.
- 패키지 설치·업그레이드 금지. 이미 설치된 도구만 쓴다.
- 명세서 내용을 외부 서비스로 보내지 않는다.
- `cfg.readOnly.priorWork` 가 있으면 그 폴더는 **S8 감사자만** 열람한다. 이전 시도의 결론에 끌려가지 않기 위해서다.

## 2-1. git
- `BASE` 는 독립 git 저장소다. **커밋은 오케스트레이터만 한다.**
  - 직원과 부장은 `git add/commit/reset/checkout/stash` 를 하지 않는다.
  - 이유: 히스토리가 단계 단위로 깔끔하게 남아야 하기 때문이다.
- `_history/` 는 git 이 있어도 유지한다. 회귀 직전 산출물을 파일로 바로 비교하기 위해서다.

## 3. 정본과 근거
- 정본 = `cfg.spec.files` 의 명세서다. `cfg.spec.allSheets` 가 true 면 **모든 시트·섹션**이 대상이다.
  - 로컬 정리본은 `00-spec/sheets/`, 색인은 `00-spec/INDEX.md` 다.
- 모든 판단에는 근거를 단다: `REQ-ID` + `00-spec/sheets/<파일>.md` 의 행.
  - 근거가 없는 판단은 **"추정"** 이라고 표시하고, `log/assumptions.md` 에 ASM 으로 등록한다.
- 모르면 지어내지 않는다. 브리핑에서 부장에게 질문한다.

## 4. ID 체계
| 접두 | 의미 | 등록 위치 |
|---|---|---|
| `REQ-<시트코드>-<원본번호>` | 원자 요구사항. 원본에 번호가 있으면 그대로 쓰고, 하위 분해 시 `.1`, `.2` 를 붙인다 | S0/S1 |
| `ENT-<이름>` | 개념 엔티티 | S2 |
| `CON-nnn` | 정본 **모순** (두 요구가 동시에 참일 수 없음) | log/contradictions.md |
| `AMB-nnn` | 정본 **모호** (해석이 여러 개) | log/contradictions.md |
| `GAP-nnn` | 정본 **누락** (스키마에 필요한데 명세에 없음) | log/contradictions.md |
| `ASM-nnn` | 설계 가정 | log/assumptions.md |
| `DEC-nnn` | 부장 결정 | log/decisions.md |
| `SCN-nnn` | 예외 시나리오 | log/scenarios.md |
| `REG-nnn` | 회귀 기록 | log/regressions.md |

번호는 해당 파일의 마지막 번호에 1을 더한다. 쓰기 전에 파일을 다시 읽는다.

## 5. 로그는 append-only
- `log/*.md` 는 **추가만** 한다. 정정은 새 항목으로 쓰고 이전 ID 를 참조한다. 예: `DEC-012 는 DEC-007 을 대체`.
- 항목 양식은 `prompts/02-templates.md` 를 따른다.

## 6. 반복과 회귀
- 프롬프트에 `반복차수=k` 가 주어진다.
- `k ≥ 2` 이면 회귀 재작업이다. 자기 산출물을 고치기 전에 `_history/<단계>-iter<k-1>/` 로 통째로 복사한다.
- 회귀 재작업은 **델타 원칙**을 따른다. 받은 리젝 항목만 고치고, 고친 곳마다 `(REG-nnn 반영)` 을 표시한다.
- 리젝 항목은 반드시 `{target: 원인 단계, reqIds, problem, evidence}` 모양이다. "전체적으로 부족" 같은 리젝은 무효다.
  - target 은 **원인이 생긴 단계**다.
    - 컬럼 누락 → S3
    - 엔티티·관계 누락 → S2
    - 요구 해석 오류 → S1
    - 정본 정리 오류 → S0
  - 정본 자체의 모순은 리젝이 아니라 CON 으로 등록하고 에스컬레이션한다.

## 7. 브리핑 모드 공통 (S1~S7)
`log/briefings/<단계>-iter<k>.md` 를 템플릿 A 대로 쓴다.
1. **받은 인풋 설명:** 부장이 읽고 오해 여부를 잡을 수 있게 구체적으로 쓴다.
2. **예외 시나리오 5~10개:** 이 단계에서 스키마를 깨뜨릴 수 있는 것. `log/scenarios.md` 에 이미 있는 것은 ID 만 참조하고 새 것만 제안한다.
3. **부장에게 묻는 질문**
4. (회귀 시) 받은 리젝 항목과 고칠 계획

브리핑 모드에서는 산출물을 만들지 않는다.

## 8. 수행 모드 공통
- 시작 전에 `log/discussions.md` 에서 이 단계·이 반복차수의 부장 토론 결과를 읽고 **반드시 반영**한다. 반영하지 못한 항목은 이유를 남긴다.
- 산출물은 역할 파일에 정해진 경로에만 쓴다.

## 9. 결과 반환
- 프롬프트 끝에 지정된 **결과 JSON 파일**에 정해진 형식으로 쓴다. 오케스트레이터는 그 파일만 읽는다.
- 내용은 산출물 파일에 있으므로 JSON 은 짧게 쓴다.

## 10. 담당 범위 — "전부 설계하되, 확정은 내 것만"
`cfg.ownership.me` 가 null 이면 이 절은 적용하지 않는다. 그 경우 모든 테이블이 `[확정]` 이다.
- 설계 범위는 **전체**다. `cfg.ownership.me` 와 `cfg.ownership.members` 모두의 DB 파트를 설계한다. 다른 사람 파트와의 접점에서 생기는 변수를 미리 잡기 위해서다.
- 담당 판정 근거 (먼저 있는 것을 쓴다):
  1. 테이블 단위: `cfg.ownership.tableOwnerSource`
  2. 행 단위: 각 시트의 `cfg.ownership.rowColumn` 열
  - 원칙: `cfg.ownership.rule`
  - 한 행에 담당이 여럿이면 테이블 소유자는 **모델·원장·백엔드 쪽**이다. 애매하면 AMB 로 등록한다.
- 모든 테이블에 등급을 붙인다.
  - `[확정: <me>]`: 사용자가 온전히 컨트롤한다. 정밀하게 설계·검증한다.
  - `[예상: <담당자>]`: 다른 담당 영역이다. 접점을 확인하려는 **예상**이며, 실제 설계는 그 담당자가 정한다.
  - `[기존]`: 기존 스키마에 이미 있는 테이블이다.
- **확정 테이블은 예상 테이블의 세부에 기대지 않는다.**
  - 확정 → 예상 참조는 `S3-schema/boundary-contracts.md` 에 **최소 가정**만 등록한다. 적을 것: 어떤 키를 참조하는지, 그 키가 다르게 설계되면 확정 쪽에서 바꿀 곳.
  - 예상 테이블의 상태값이나 내부 컬럼으로 확정 테이블의 무결성을 지키게 설계하지 않는다.
  - 예상 테이블과의 연결은 **FK 한 줄 제거·교체로 분리할 수 있는 수준**으로 둔다.
  - 기존 테이블로의 FK 는 제한이 없다.

## 11. 화면 기획은 바뀐다 — 변경에 강한 스키마
`cfg.screenPlan` 이 `final` 이 아니면 강하게 적용한다.
- **사실을 저장한다.** 누가·언제·무엇을 했는지, 무엇의 원인이 된 데이터를 남긴다.
  - 화면의 단계·배지·탭은 사실에서 계산하는 값이나 코드로 둔다.
- **바뀔 수 있는 값 목록은 코드 테이블에 둔다.** 의미가 고정된 값만 enum 으로 한다. 예: 방향, 법적 이벤트 종류.
- **화면 전용 정보는 컬럼으로 만들지 않는다.** 정렬 순서, 표시 라벨, 그룹핑 같은 것이다.
- **필수 여부가 화면 기획에 달린 항목은 일단 nullable** 로 두고 ASM 으로 기록한다.
- **미확정 부가 항목은 테이블당 최대 1개의 JSON 컬럼**으로 흡수할 수 있다.
  - 조회 조건·조인·무결성에 쓰지 않는 값만 넣는다.
  - 들어갈 수 있는 키 목록을 문서화한다.
  - 검색·필터 대상이 되면 정식 컬럼으로 올린다.
- **인덱스는 확정된 접근 경로에만 건다.** 권한 스코프, FK, 시간순, 외부 멱등 키 같은 것이다.
- **판단 기준:** "화면이 바뀌면 마이그레이션이 필요한가?" 컬럼 추가로 끝나면 좋은 설계다. 의미 변경이나 테이블 분해·병합이 필요하면 나쁜 설계다.

## 12. 오버엔지니어링 금지 — 유연성보다 단순성이 먼저
- **테이블은 아래 중 하나 이상일 때만 분리한다.** S3 는 테이블마다 해당 번호를 적는다.
  1. 생명주기가 다르다
  2. 1:N 이상의 반복이 있다
  3. 접근 권한이나 보존기한이 다르다
  4. 쓰기 주체(담당)가 다르다
  5. 정본이 별도 테이블로 명시했다
- **금지:**
  - 이유 없는 1:1 분리
  - EAV·범용 key-value 테이블
  - "아무 엔티티나 가리키는" 다형 테이블. 단, 정본이 장부 하나로 요구하는 감사 로그·동의 원장 등은 예외다.
  - 코드 종류마다 테이블 만들기. 코드 테이블은 그룹 컬럼을 둔 1개로 통합한다.
  - "나중에 필요할지도" 만을 근거로 한 테이블·컬럼
- **테이블 예산:** 기준선은 `cfg.baseline.source` 다. 없으면 S2 에서 부장이 승인한 엔티티 목록이 기준선이다.
  - 기준선에 없는 신규 테이블은 하나하나 부장 승인(DEC)이 필요하다.
  - 증감은 `S3-schema/table-budget.md` 에 적는다.
- 유연성과 단순성이 부딪히면 **단순성**을 고른다. 유연성은 "나중에 추가하기 쉬운가"로 판단한다.

## 13. 스키마 스타일
- `cfg.db.conventionsFrom` 이 `existing` 이면 기존 스키마의 관례를 그대로 따른다. 명명, 매핑, PK 타입, 타임스탬프, soft delete 등이다.
- 통합 모드(`cfg.existingSchema.mode`):
  - `extend`: 기존 테이블로 해결되면 재사용·FK 참조한다. 기존 모델 변경은 `S3-schema/existing-model-changes.md` 에 모은다.
  - `standalone`: 기존 스키마 없이 설계한다.
